# Lessons Learned

作業中のミス・ハマりどころと、その再発防止策を貯めておく場所。
新しいミスをしたら、その場でここに追記する（日付・何が起きたか・原因・対策）。
作業を始める前に「チェックリスト」だけでも読む。

## チェックリスト（要約）

- [ ] 長時間ジョブ（学習・生成・ダウンロード・corpus処理）は `nohup` か tmux で起動し、全出力をログファイルに残す
- [ ] ログを `tail` / `head` / `grep` で絞って保存しない。絞るのは保存した後、読むときだけ
- [ ] 高速化を試したときは、tok/sだけでなく **lossが正常に下がるか** も見る
- [ ] corpusを学習に入れる前に、実際の文書を目で見る（特に除去された要素の痕跡）
- [ ] configの値（micro batchなど）は、計測で確かめてから書く
- [ ] 互換性に影響する変更（data RNG、tokenizer、sampler）は、実行中・再開予定のrunがないか確認し、docsに書く
- [ ] 本番環境（`.venv`）を壊しうる実験は、別のvenvで行う

## 記録

### 2026-10-03: ログを `tail -n 40` で絞ったせいでエラー本文が消えた

- 何が起きたか: `scripts/bench_compile.sh` で `torchrun ... 2>&1 | tail -n 40` としていた。モデル全体compileが失敗したが、ログに残ったのはtorchrunの `ChildFailedError` の要約だけで、子プロセスの本当のTracebackは消えていた。原因を調べるために再実行が必要になった
- 原因: torchrunは、子プロセスのTracebackを先に出力し、最後に親の要約を出力する。末尾だけを残すと要約しか残らない
- 対策: 全出力をファイルに保存する（`> logs/<name>.log 2>&1`）。絞るのは保存した後、読むときだけにする。`bench_compile.sh` は修正済み（mode別に `logs/bench-compile-torch27-<mode>.log`）
- 結果: 全文を残して再実行したところ、本体は `CUBLAS_STATUS_EXECUTION_FAILED`（bf16 GEMM）だった
- 一般化: torchrun / DDP のエラーは「最初の」Tracebackが本体。`grep -n Traceback` で先頭のものを読む

### 2026-10-03: 前景で走らせた生成ジョブがツールのエラーと一緒に止まった

- 何が起きたか: `generate_samples.py` 2本を `&` + `wait` で前景のシェルから起動したところ、ツール呼び出しが内部エラーで終了し、生成プロセスも途中（7/8プロンプト）で止まった。出力jsonlは最後に一括で書き出す仕様のため、何も残らなかった
- 対策: 数分以上かかるGPUジョブは `nohup ... > log 2>&1 &` で起動し、完了待ちは別に行う。出力を最後に一括で書くスクリプトは、途中で落ちると何も残らないことを意識する
- 再発（同日）: 完了待ちの `until ...; do sleep; done` を前景で長時間走らせたところ、ツールが再び内部エラーで落ちた。ジョブ本体は `nohup` だったので無事だった → **長い待ちは `run_in_background` で行い、前景では待たない**
- 関連: 10/2のセッションもtmux外で作業していて途中で終了した。学習は `nohup` していたので生き残った

### 2026-10-03: layer単位compileは速くなったが、学習が壊れていた

- 何が起きたか: torch 2.7.1 + layer単位compileで、tok/sは 38.2k → 42.4k（+11%）、メモリも減った。しかしlossは初期値の約10.9のまま、grad_normは1e7台で、学習がまったく進んでいなかった
- 教訓: 高速化の評価はスループットだけで判断しない。同じseed・同じ設定のeagerと **loss曲線を並べて** 比べる（eagerはstep 25で7.74）
- 対策: ベンチmarkのconfigでもloss・grad_normを毎回ログに出し、比較表にlossの列を入れる

### 2026-10-03: HF版Wikipediaはtextから数式が消えていて、モデルが「空白の穴」を学習した

- 何が起きたか: run-002の生成で「 は、 が に対応できる」のような、助詞だけが並ぶ文が出た。corpusを確認すると、`wikimedia/wikipedia` のtextでは `<math>` が除去されて空白だけが残っていた（先頭20万文書のうち、数学系で1,378件）
- 教訓: 外部データセットは、「何が除去・変換されているか」を学習前に確認する。統計（文字数・日本語比率）だけでは気づけない
- 対策: corpusを入れる前に、ランダムに数十件と、専門分野（数学・コード・表）の文書を数件見る。cleaningに「助詞の前に空白が残っている」パターンを検出するfilterを入れる候補

### 2026-10-02: dryrun configのmicro batch 8がOOMした

- 何が起きたか: dryrun configは micro batch 8 で書いていたが、313M / ctx4096 / A6000 ではOOMになった。計測の結果、4が上限だった
- 対策: configは計測してから書く。新しいサイズやctxにするときは、合成データで短くスループット・メモリを測ってから本番のconfigを作る

### 2026-10-03: samplerの乱数の引き方を変えると、resumeの再現性が崩れる

- 何が起きたか（未然に防いだ）: `pretrain.py` を複数source対応にした際、単一sourceでも乱数を1行ずつ引く方式に変わった。変更前に始めたrunをresumeすると、data順が一致しなくなる
- 対策: samplerやRNGを変えるときは、実行中・再開予定のrunがないかを確認する。変更点はdocs（progress）に明記する

### 2026-10-03: `pgrep -f` が自分を呼んだシェル自身にヒットした

- 何が起きたか: `pgrep -f smoke-mix || rm -rf checkpoints/bench/smoke-mix` を1行のコマンドで実行したところ、プロセスはもう終わっていたのに `pgrep` がヒットし、削除が飛ばされた
- 原因: `pgrep -f` はコマンド行全体を照合する。自分自身（pgrep）は除外されるが、そのコマンド行を含む親の `bash -c "..."` は除外されない
- 対策: 待機・生存確認に使う `pgrep -f` のパターンは、呼び出し元のコマンド行に含まれない文字列にする。スクリプトのファイル内で使うなら、そのスクリプト名と別の文字列にする（`run_003_after_corpus.sh` の `pgrep -f run_corpus_v003.sh` は問題ない）。PIDファイルを使う方が確実
